# Step 2: durable sensor scans

Step 1 already supplies dual TGS validation/storage. Step 2 adds persisted scan
sessions, server-derived provider/device identity and durable acquisition receipts.
No physical sensor or glucose model is needed to exercise the full workflow.

## What changed

The old listener existed only in one process, accepted any upload for the selected
patient and remained armed after saves. It could not distinguish an old scan from
a replacement for the same patient, or safely recognize a retry after a lost
response. Sessions now live in `scan_sessions`, with one active explicit session
per provider. `sensor_acquisitions` records immutable acquisition identity/payload
hash and the resulting reading. SQLite uniqueness and atomic status updates protect
against concurrent workers and replays. No process-local dictionary controls scans.

States: `pending` → `collecting` (device heartbeat) → `completed` (successful
ingestion). Active sessions may instead become `cancelled`, `expired` or `replaced`.
Exactly one acquisition completes a session. Explicitly starting another session
replaces the provider's previous active session, even for the same patient. The
default deadline is 900 seconds; `/scans` can request 15–900 seconds. Heartbeats
never extend it. Expiry is persisted when the provider/device next accesses the
workflow; acceptance checks the absolute deadline regardless of polling frequency.

## API

All paths are under `/readings`; existing ingestion/history/WS paths remain.

| Operation | Access and behavior |
| --- | --- |
| `POST /scans` | Medical Bearer JWT; owned `patient_id`, optional `source` (`device` default / `manual`), `sensor_configuration`, `timeout_seconds` |
| `GET /scans/{session_id}` | Owning provider or matching authenticated device; status, binding, UTC timestamps, connection freshness and result IDs |
| `POST /scans/{session_id}/heartbeat` | Matching device only; reports collection/contact, leaves deadline unchanged |
| `POST /scans/{session_id}/cancel` | Owning provider; idempotent cancellation of an active session; completed readings are not undone |
| `POST /sensor` | Matching device or medical manual entry; validates and atomically completes/saves one acquisition |
| `GET /acquisitions/{acquisition_id}` | Owning provider or matching device; recover saved result after an interrupted/ambiguous request |
| `POST /listener/start` | Existing provider UI adapter: creates a default device scan and returns existing `armed`, `patient_id`, `patient_name`, `session_id`, `message` fields |
| `GET /listener/armed-patient` | Existing provider/device polling adapter; returns exact active session/device identity and expiry; authenticated device contact updates freshness |
| `POST /listener/stop` | Existing provider adapter; optional session ID prevents a stale tab from cancelling a newer scan |

Session snapshots include `device_connection`: `unknown` until contact,
`connected` while last contact is under 60 seconds old, `disconnected` thereafter,
or `not_applicable` for manual input. This is **contact freshness**, not proof of
physical sensor health. Disconnection does not fabricate a reading or extend the
session. A reconnected matching device may resume until the absolute deadline.

The configured device's key maps to its server-side `BREATHDX_DEVICE_MEDICAL_ID`
and `BREATHDX_DEVICE_ID` (default `esp32-default`). Use a stable logical identifier
for the actual provisioned device. Client-supplied provider/device identity is
rejected. Existing configuration provisions one logical device/key, not a fleet;
do not share that key among devices that need separate audit identities.
Manual input is labelled `manual-provider-{provider_id}`, never as ESP32 data.

## Acquisition and retry contract

Example **synthetic** completion payload; use the IDs returned/generated by the
workflow rather than submitting these placeholders:

```json
{
  "patient_id": 1,
  "scan_session_id": "UUID_FROM_THE_ARMED_SESSION",
  "acquisition_id": "NEW_UUID_FOR_THIS_ACQUISITION",
  "sensor_configuration": "tgs822_tgs2620",
  "tgs822_raw_adc": 1200,
  "tgs2620_raw_adc": 1800,
  "tgs822_baseline_adc": 1400,
  "tgs2620_baseline_adc": 500,
  "temperature": 28.5,
  "humidity": 65.0
}
```

Use a UUID, in hex or standard hyphenated form. The backend normalizes it to hex.
Generate an acquisition ID once before submitting. Preserve that ID, the exact
session and payload when recovering/retrying; a new physical acquisition needs a
new ID and a new session. Devices must send both identifiers. Old device packets
without them are now rejected with 422 because inferring the current session would
allow replaced/late scans to be misassigned. The checked-in firmware sends both,
reports a heartbeat, and does not automatically reacquire into an ambiguously
submitted session. Real firmware needs persistent pending-payload storage if it
must recover after power loss; that capability has not been implemented here.

Same ID and same authenticated binding/payload → 200 with the original reading
and `duplicate: true`; no new row or repeated WS event. A used ID with a changed
payload/session/source/device → 409 (or 404 for inaccessible identities). A new
acquisition in a completed/cancelled/expired/replaced session → 409. A valid replay
of an already saved acquisition is a recovery read, not a new terminal-session
submission. Receipt identity survives deliberate reading deletion: retrieval/replay
then returns 410 and cannot recreate the record.

On a timeout/network interruption/503, check `GET /acquisitions/{id}` and
`GET /scans/{session_id}`. A 404 receipt does not prove the original request has
finished; retry only with the **same** IDs/payload. SQLite contention may produce
a sanitized 503; the same recovery rule applies. Validation 422, authorization
401/403, inaccessible object 404 and lifecycle/conflict 409 remain distinct.

Provider manual entry can omit `scan_session_id`; the backend creates and completes
an implicit manual session without replacing a device listener. Older manual
clients can still omit acquisition IDs for compatibility, but such requests cannot
provide retry identity: the server assigns an ID for each accepted request. The
active web form generates an ID and retains it for unchanged-payload retries.
All new saved readings have provider/device/session/acquisition provenance. Old
historical rows keep their original values and **null** new provenance fields;
unknown historical device/session identities are never invented.

TGS ADC inputs remain required integers 1–4094, baselines optional integers 0–4094,
temperature finite −40–80 °C and humidity finite 0–100%. Baselines are independent
observations, not subject to the old MQ breath threshold. New TGS results keep
`acetone_ppm`, `diabetes_level` and `predicted_bgl` null, with calibration unverified.

## Persistence and clients

Session completion, reading and acquisition receipt commit in one transaction.
Failure rolls back them together. A lost commit acknowledgement can be resolved
from its receipt. Broadcast failure never undoes a saved acquisition. Medical WS
events remain filtered by provider/optional patient and include the new provenance.
The web listener filters the exact session and polls its completed receipt even
when a live socket missed the event. REST history/latest routes supply saved scans
to the unchanged patient mobile workflow. Late cancellation does not delete readings.
Patient deletion is refused when readings **or scan history** would be orphaned.

## Safe upgrade

Stop the API/other writers. After the Step 1 migration, from `backend` run:

```powershell
.\venv\Scripts\python.exe -B migrate_scan_workflow.py
```

Optional `--source` and `--backup` select a database and a new private backup file.
The default source is anchored to this backend directory. The migration verifies a
consistent backup under ignored `backups/`, then transactionally adds the two new
tables, uniqueness indexes and four nullable reading provenance columns. It compares
every original provider/patient/reading value and row count with the backup and
checks integrity/FKs before committing. Existing tables/reading history are not
rebuilt or recalculated. It is idempotent, refuses partial schemas and never
overwrites a backup. Failed DDL rolls back. Startup requires the current schema
and uniqueness indexes before serving the app; `create_all()` is not a migration.

To restore, stop every writer and restore the verified private backup together
with the matching pre-Step-2 code, handling SQLite journals/WAL files correctly.
Never restore over an active server. Backups contain private health data.

## Hardware-free verification

Run the complete regression suite with the existing environment:

```powershell
.\venv\Scripts\python.exe -B -m unittest discover -s tests -q
```

For only the simulated HTTP scan walkthrough scenarios:

```powershell
.\venv\Scripts\python.exe -B -m unittest discover -s tests -p test_scan_workflow.py -v
```

Tests create their own private app, synthetic accounts, simulated device key and
ADC/environment observations. They do not import `main.py`, touch the working
patient database, connect hardware, or load real model artifacts. File-based tests
cover competing workers and database reopening; migration tests cover preservation
and rollback. These are software checks, not sensor calibration or clinical evidence.
